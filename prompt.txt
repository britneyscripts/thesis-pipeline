### Scaling, Normalization & Logging Guidelines

1. **URL Normalization**:
   - Raw input lists can contain domains without protocols (e.g., `domain.com/path`).
   - The ingestion/first-stage parsing process must validate and automatically prepend `https://` to ensure down-stream Python scripts do not crash with `MissingSchema` exceptions during execution.

2. **SKU Slugification & Directory Structure**:
   - SKU names should be converted into clean, filesystem-safe slugs (e.g., `"SKU 1 — iPhone 17 Pro"` -> `iphone-17-pro`).
   - Slugs should be lowercase, accent-free, and hyphenated, serving as the subdirectory names under the `extractions/` folder.
   - When scaling or modifying the SKU list substantially, old extraction folders should be versioned and archived (e.g., renamed to `extractions_v01`) to maintain clean run states.

3. **Unified Structured Logging**:
   - Each script (content, crux, pagespeed) must produce a companion log file (`*_log_YYYYMMDD.json`) inside the date-specific subdirectory for the SKU.
   - All logs must adhere to a strict, standardized pattern to simplify parsing and analysis:
     ```json
     {
       "Store Name": {
         "status": "success" | "error",
         "errors": ["Detailed error string if failed"],
         "duration_seconds": 12.34,
         "metrics_found": ["LCP", "CLS", ...]
       }
     }
     ```

4. **Performance & Timeout Monitoring**:
   - PageSpeed Insights online queries are synchronous, sequential, and run full Lighthouse audits. 
   - A single run over a high quantity of URLs (e.g., 27 URLs with mobile and desktop strategies) can take 35–45 minutes due to regular 60-second read timeouts when bot-protection filters (e.g. Cloudflare, Akamai) block the Google Lighthouse runner.
   - Logging `duration_seconds` and timeout exceptions is critical to identify and isolate slow retailers from normal API latency.

5. **GCP Migration & Cloud Storage Integration**:
   - **Hybrid Environment Configuration**: The helper `scripts/config.py` acts as a unified secrets provider. It reads local `.env` first, falling back to Google Cloud Secret Manager (`projects/{GCP_PROJECT_ID}/secrets/{SECRET}/versions/latest`) when deployed to GCP.
   - **Cloud Storage (GCS) Integration & Local Fallback**: The `save_json(data, blob_path)` function dynamically detects the environment by checking for the presence of the `GOOGLE_CLOUD_PROJECT` environment variable:
     - Local Mode: Automatically directory-structures and writes the JSON files locally matching the original nested structures (`extractions/{blob_path}`) if the variable is not set.
     - GCS Mode: Uploads the JSON directly to a Google Cloud Storage bucket (defaulting to `ghostprod-extractions` or customized via `GCS_BUCKET_NAME` environment variable) using the google-cloud-storage client if the variable is set.
   - **Sequenced Pipeline Execution**: The master script `scripts/run_pipeline.py` executes scripts sequentially and records individual process exit codes, logging details of each script run (success, duration, error) to `extractions/pipeline_runs.log`, and terminating with a representative code (0 for complete success, 1 for partial success, 2 for complete failure).
